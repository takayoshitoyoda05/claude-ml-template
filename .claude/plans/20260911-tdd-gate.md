## 目的

エージェントの「実装を直す代わりにテストを書き換えて通す」失敗モードを、既定off の
補助線(PreToolUse ブロック)で機械的に止める。あわせて tdd スキルの Red を
実行証拠つきに強化し、ブロック件数をログに残して効果測定できる状態にする。

## 設計判断(本計画で確定)

| 項目 | 決定 | 理由 |
|------|------|------|
| チェーン内の位置 | state_gate.py の**後ろ**(末尾)に登録する | 既存3本の判定・ブロック文言に一切影響を与えない位置で、追加分の切り分けが容易(登録順=記述順で読める)。既定off の実験機能を、秘密情報・スコープという恒久ガードより前に置く理由が無い |
| センチネル・ログのパス解決 | codex_gate.py と同じく cwd 基準の相対定数(`.claude/checkpoints/tdd_red.json`・`tdd_gate_blocks.log`・`tdd_red_last.log`) | 既存フックと流儀を揃えると、verify-hooks も同じ「一時ディレクトリに cd して実行」方式で汚染なく検証できる |
| 3フックの配布方法 | `_staging_tdd_gate.py` に本体ソースを文字列として埋め込み、`--root` で書き出す | 保護パスへ直接書けないため。`--root` を持たせるとサンドボックスへ適用でき、ユーザー適用前でも pytest で RED から GREEN まで回せる |
| フックの依存 | 3本とも標準ライブラリのみ。`_common` 等の同居モジュールを import しない | サンドボックス(`--root` 先の一時ディレクトリ)には hooks 一式が無く、import すると適用検証が成立しない |
| settings.json の書き換え | JSON 全体を再出力せず、state_gate.py の登録ブロック直後への**テキスト挿入**で行う | 全体再整形は無関係な差分を生み、最小diff規律に反する。適用済み判定は `tdd_gate.py` の出現数で行う |
| settings.json 不在時の挙動 | 登録だけを `SKIP` と表示して **exit 0** を保つ | サンドボックス適用(pytest)では settings.json が無いことがあるため。実リポジトリには常に存在する |
| 受け入れテストの二本立て | `tests/test_tdd_gate.py`(サンドボックス)を主、verify-hooks ケース(実リポジトリ)を従として**両方**書く | 設計書 R-002〜R-012 の検証方法が verify-hooks ケースで固定されている一方、テストファーストにはユーザー適用前に実行できる経路が要る |
| R-006 の検証手段 | hypothesis は導入せず、verify-hooks の**表記変形ケース**(絶対/相対/symlink/前方一致)で行う | 設計書が両方を許容しており、新規依存を増やさない方が既存の検証経路に乗る |
| テストコマンドの実行 | `shell=True` + `timeout` 指定。タイムアウトは「Red 不成立(センチネルを作らない)」「解除不可(センチネル保持)」として扱う | `_staging_enforce_eval_timeout.py` が確立した整理(時間切れ=検証が完了していない)と同じ向き。fail-closed |
| センチネル/ログの保護パス追加 | **行わない**(`_common.py` は触らない) | 偽装への完全耐性は設計書 non-goal 4。`/checkpoints/` は既に ARTIFACT として Edit/Write が塞がれており、追加保護の費用対効果が薄い |

## リスク

- **fail-closed が強すぎる**: 壊れたセンチネル + `CLAUDE_TDD_GATE=1` では記録済みテストファイルへの
  編集が止まり続ける。ブロック文言に3つの脱出路(unlock / `--rearm` / `CLAUDE_TDD_GATE=0`)を必ず含める
  (Step 2 注意3、PC-5・PC-10 が番人)。
- **verify-hooks が実リポジトリを汚す**: 検証中にセンチネルを残すと、以降のセッションで
  (ゲートを有効にしている利用者の)編集を止めうる。全ケースを一時ディレクトリで実行し、
  PC-19 で「実行後にセンチネルが存在しない」ことを検査する。
- **チェーンへの4本目の追加**: 同一 matcher に4本目を足した実機挙動(既存3本が従来どおり走ること)は
  ユーザー適用後の Step 6 でしか確認できない。既存3本の登録内容には手を触れず、末尾挿入に限定して
  影響範囲を最小化する。
- **staging 適用後は自己修正できない**: 3フックは保護パス配下になるため、不具合が出た場合の修正も
  staging の再実行が必要になる。ロールバックは (a) `CLAUDE_TDD_GATE` を未設定に戻す(既定off なので
  実害が消える)、(b) ユーザーが `!` 実行で settings.json の登録行と `.claude/hooks/tdd_*.py` 3本を削除、
  (c) フック追加前のコミットへ戻す(`.claude/hooks/` は追跡対象なので git で復元できる)。
- **Bash 迂回**: `sed -i` やリダイレクトによるテスト編集は検知できない(設計書 non-goal 1・ADR-0006)。
  補助線として受け入れる。
- 検討した代替案と不採用理由:
  - **案A: Stop フックでの事後検知(codex_gate 型)** — Bash 迂回も拾えるが、改変が起きた後の検知になり
    差し戻しコストが高い。ADR-0006 で PreToolUse 即時ブロックに決定済み。不採用。
  - **案B: settings.json を `json.load` / `json.dump` で書き換える** — 実装は素直だが全体が再整形され、
    無関係な差分が出て最小diff規律に反する。不採用(テキスト挿入を採用)。
  - **案C: pytest を使わず verify-hooks ケースだけで受け入れを行う** — 重複は減るが、staging 適用
    (ユーザーの `!` 実行)まで1件もテストを走らせられず、テストファーストが成立しない。不採用。
  - **案D: センチネルと blocks.log を `PROTECTED_PATH_PATTERNS` に追加する** — 偽装耐性は上がるが、
    `_common.py` の変更で staging の影響範囲が広がる一方、`/checkpoints/` は既に Edit/Write が塞がれて
    おり増分が小さい。設計書 non-goal 4 とも整合しないため不採用。
  - **案E: R-006 を hypothesis のプロパティテストで書く** — 網羅性は高いが新規依存が増え、
    設計書が許容する verify-hooks の表記変形ケースで足りる。不採用。
- 未確認の仮定: tdd_red.py / tdd_gate.py / tdd_unlock.py はいずれも新規で、既存の同名フックと衝突しない / 検証: `ls .claude/hooks` / 期待: `tdd_` で始まるファイルが1件も表示されない
- 未確認の仮定: guard_bash がユーザー `!` 実行専用として扱うフックは2本のみで、tdd 系スクリプトはエージェント自身が実行できる / 検証: `grep -c "def .*_execution" .claude/hooks/guard_bash.py` / 期待: 2
