## 目的

エージェントの「実装を直す代わりにテストを書き換えて通す」失敗モードを、既定off の
補助線(PreToolUse ブロック)で機械的に止める。あわせて tdd スキルの Red を
実行証拠つきに強化し、ブロック件数をログに残して効果測定できる状態にする。

## 設計判断(本計画で確定)

| 項目 | 決定 | 理由 |
|------|------|------|
| センチネル・ログのパス解決 | **スクリプト自身の配置**から求めたリポジトリルート基準(`Path(__file__).resolve().parents[2]` = `.claude/hooks/` の親の親)で `.claude/checkpoints/tdd_red.json` ・ `tdd_gate_blocks.log` ・ `tdd_red_last.log` を解決する | サブディレクトリから起動されても同一のセンチネルを参照させるため(設計書4節の不変条件)。cwd 基準だと `cd src && tdd_red.py` のような起動で別のセンチネルが生まれ、ゲートが素通りする |
| 編集対象パスの解決 | **ペイロードの `cwd`**(無ければ `os.getcwd()`)基準で絶対化し、realpath で照合する(`guard_scope.py:111-128` と同一) | ツールが編集する基準はセッションの cwd であり、フックの配置とは無関係。**センチネル(スクリプト配置基準)と編集対象(ペイロード cwd 基準)で解決基準が異なる**ことを実装時に取り違えないこと |
| パス照合の正規化 | `os.name == "nt"` のときだけ小文字化する正規化関数を**3フックそれぞれに standalone で実装**する(`_common.py:86-96` の `CASE_INSENSITIVE_FS` / `path_for_match()` と同じ規則) | Windows では `TESTS/TEST_X.PY` と `tests/test_x.py` が同一実体になり、正規化しないと大文字表記でゲートを迂回できる。`_common` は import できない(自己完結の要件) |
| 記録時の実行ディレクトリ | センチネルに `recorded_cwd`(絶対パス)を持たせ、tdd_unlock.py は**記録された cwd でテストコマンドを再実行**する。`recorded_cwd` が存在しない場合は非0終了しセンチネルを保持する | 相対パスを含むテストコマンドが別ディレクトリからの解除実行で偽陽性/偽陰性になるのを防ぐ(設計書4節) |
| センチネルのスキーマ検証 | 必須5キー(`test_command` / `test_files` / `recorded_cwd` / `recorded_at` / `log_path`)がすべて存在し、`test_files` が**非空の文字列配列**、他4キーが**文字列**であることを検証する。1つでも満たさなければ fail-closed(exit 2)。例外は捕捉し traceback を出さない | 型不正を素通りさせるとゲートが無効化し、traceback を出すとフックが落ちて fail-open になる(設計書4節) |
| fail-closed のブロック範囲 | 読めない/パースできない/必須キー欠落/型不正/`test_files` 空のセンチネルでは、**対象ツール(Edit/Write/NotebookEdit)の全パスの編集**をブロックする | 照合不能なのでどのパスが保護対象か判定できない。ブロック文言に「照合不能のため全編集を停止中」である旨と3つの脱出路を必ず含める |
| チェーン内の位置 | state_gate.py の**後ろ**(末尾)に登録する | 既存3本の判定・ブロック文言に影響を与えず、追加分の切り分けが容易。既定off の実験機能を、秘密情報・スコープという恒久ガードより前に置く理由が無い |
| 3フックの配布方法 | `_staging_tdd_gate.py` に本体ソースを文字列として埋め込み、`--root` で書き出す | 保護パスへ直接書けないため。`--root` があればサンドボックスへ適用でき、ユーザー適用前でも pytest で RED から GREEN まで回せる |
| staging の適用モデル | **前検証 → 書き込みの2段**。前検証(settings.json が存在し JSON パース可能、対象 matcher がちょうど1件で `hooks` が配列、既存の登録数と順序が想定どおり、書き出し先が既存の別内容と衝突しない)に1つでも失敗したら**何も書かずに非0終了**。書き込みは (1) hooks 3本を一時名で書いて `os.replace`、(2) **最後に settings.json を単一の `os.replace`** の順で行い、途中で失敗したら**この適用で新規配置した tdd_*.py と一時ファイルを削除して適用前状態に復元**し非0終了する(新規ファイルのみなので削除=復元) | 半適用(フックだけ置かれて未登録、settings.json だけ壊れる)は保護パス配下で起き、エージェントが直せない状態になる(設計書 R-019・R-020) |
| settings.json 不在時の挙動 | 通常適用では**エラー(非0終了・何も書かない)**。登録を省くのは `--hooks-only` を**明示指定**したときだけで、その場合も settings.json を新規作成しない | `--root` の誤指定や不完全な checkout を「成功」と誤報しないため。サンドボックス用途はフラグで意図を明示させる |
| settings.json の判定と検査 | 適用済み判定・前検証・smoke はすべて **JSON パースによる意味検査**(matcher 文字列・command 文字列・登録数・順序)で行う。書き込み自体は対象箇所へのテキスト挿入で行い、全体の再整形はしない | 文字列出現数だけの判定はコメントや別 matcher への混入を見逃す。一方で全体再整形は無関係な差分を生み最小diff規律に反するため、判定と書き込みで手段を分ける |
| フックの依存 | 3本とも標準ライブラリのみ。`_common` 等の同居モジュールを import しない | サンドボックス(`--root` 先)には hooks 一式が無く、import すると適用検証が成立しない |
| 受け入れテストの対象解決 | `tests/test_tdd_gate.py` は**2経路**でフックを取得する: (1) `_staging_tdd_gate.py` があればサンドボックスへ `--root` 適用、(2) 無ければ**追跡済みの `.claude/hooks/tdd_*.py` をサンドボックスへ写す**。どちらも無い場合は skip ではなく **FAIL** する番人テストを1件置く。staging 固有のケース(冪等・半適用・書き込み失敗・`--hooks-only`)だけが経路(2)で skip になる | staging は CONTEXT.md の規約どおり gitignore 対象のままにしつつ、クリーン環境で全件 skip → 「失敗0」という偽陰性を塞ぐ。フック本体は追跡対象なので経路(2)が必ず成立する |
| 受け入れテストの二本立て | `tests/test_tdd_gate.py`(サンドボックス)を主、verify-hooks ケース(サンドボックスに置いた写し)を従として**両方**書く | 設計書 R-002〜R-012 の検証方法が verify-hooks ケースで固定されている一方、テストファーストにはユーザー適用前に実行できる経路が要る |
| verify-hooks でのフック起動方法 | 実リポジトリのフックを直接叩かず、`mktemp -d` したサンドボックスの `.claude/hooks/` に**写しを置いてそれを実行**する | パス解決がスクリプト配置基準になったため、実物を叩くと実リポジトリの `.claude/checkpoints/` にセンチネル・ログを書いてしまう |
| ps1 の品質担保 | 実行は pwsh のある環境に限られるため、**CI に構文パース検査(`Parser::ParseFile`)を1ステップ追加**する。実行(全ケース PASS)までは CI に求めない | 構文エラーの ps1 が長期間気付かれずに残るのを防ぐ最小の手当て(設計書 R-021)。実行まで入れると Windows 依存のケース整備が必要になり本計画の範囲を超える |
| R-006 の検証手段 | hypothesis は導入せず、verify-hooks の**表記変形ケース**(絶対/相対/symlink/前方一致)で行う | 設計書が両方を許容しており、新規依存を増やさない方が既存の検証経路に乗る |
| テストコマンドの実行 | `shell=True` + `timeout` 指定。タイムアウトは「Red 不成立(センチネルを作らない)」「解除不可(センチネル保持)」として扱う | `_staging_enforce_eval_timeout.py` が確立した整理(時間切れ=検証が完了していない)と同じ向き。fail-closed |
| シェルの OS 依存 | `shell=True` は記録時の OS のシェル(POSIX は `/bin/sh`、Windows は `cmd.exe`)で解釈される。**記録した OS と異なる環境での再実行は保証外**とし、その旨を tdd スキルと README に1行明記する。OS 判定キーはセンチネルに持たせない | センチネルは gitignore 対象の `.claude/checkpoints/` にあり、同一チェックアウトを別 OS で跨いで使う運用は想定外。キーを増やすより明記で足りる(YAGNI) |
| センチネル/ログの保護パス追加 | **行わない**(`_common.py` は触らない) | 偽装への完全耐性は設計書 non-goal 4。`/checkpoints/` は既に ARTIFACT として Edit/Write が塞がれており、追加保護の費用対効果が薄い |

## 事後条件(postconditions)

期待値は設計書の受け入れ条件(R-001〜R-021)と上記「設計判断」から導いた。実装前に Step 1 でテスト化する。
サンドボックス = staging の `--root` 適用、または追跡済みフックの写しで組んだ一時ディレクトリ。
「記録済みテストファイル」= 直前の `tdd_red.py --files` で渡したファイル。
「ツリーマニフェスト」= 対象ディレクトリ配下の全エントリについて (相対パス, 種別(file/dir/symlink),
symlink 先, mode, 通常ファイルのみ sha256) を集めたもの。

|----|------|------|---------------|------|

## リスク

- **fail-closed のブロック範囲が広い**: 壊れた/型不正のセンチネル + `CLAUDE_TDD_GATE=1` では
  記録済みテストファイルに限らず **Edit/Write/NotebookEdit の全編集**が止まる(設計書4節の決定)。
  ブロック文言に「照合不能のため全編集を停止中」である旨と3つの脱出路(unlock / `--rearm` /
  `CLAUDE_TDD_GATE=0`)を必ず含める(Step 2 注意3、PC-10 が番人)。
- **Windows での照合は実地検証できない**: 大文字小文字の正規化は `_common.py` と同じ規則で
  standalone 実装するが、検証は POSIX 上の静的検査(正規化関数の存在)にとどまり、
  Windows 実機での挙動は**保証外**。実機確認は pwsh/Windows 環境を持つ利用者の報告に委ねる。
- **クリーン環境での偽陰性**: staging は gitignore 対象のため、クリーン clone では staging 依存の
  テストが skip になる。フック本体が追跡対象である性質を使う2経路方式と番人テスト(PC-28)で
  「全件 skip で失敗0」を塞ぐ。
- **解決基準の取り違え**: センチネルはスクリプト配置基準、編集対象はペイロード cwd 基準という
  2基準が同居する。片方に寄せると「サブディレクトリ起動で素通り」か「編集対象の誤判定」の
  どちらかが起きる(PC-7・PC-22 が両方向の番人)。
- **verify-hooks が実リポジトリの状態を壊す**: 実物のフックを叩くと実リポジトリの
  `.claude/checkpoints/` にセンチネル・ログを書き、利用者の進行中の Red 記録を破壊しうる。
  必ずサンドボックスへの写しを実行し、PC-19 の前後ハッシュ比較で担保する。
- **staging の半適用・誤適用**: 前検証を通ってから書く2段適用にし、書き込みは
  「hooks → 最後に settings.json を単一 `os.replace`」の順とし、途中失敗時は新規配置分を削除して
  復元する(PC-23・PC-24・PC-29)。settings.json 不在は `--hooks-only` の明示指定が無い限り
  エラーにする(PC-26)。
- **CI は ps1 を実行しない**: 構文パース検査のみのため、ps1 の**実行時**の退行(ケースの
  期待値ずれ)は検知できない。マーカー1対1対応(R-016)と pwsh 環境での手動実行で補う。
- **チェーンへの4本目の追加**: 同一 matcher に4本目を足した実機挙動(既存3本が従来どおり走ること)は
  ユーザー適用後の Step 7 でしか確認できない。既存3本の登録内容には手を触れず、末尾追加に限定する。
- **staging 適用後は自己修正できない**: ロールバックは (a) `CLAUDE_TDD_GATE` を未設定に戻す
  (既定off なので実害が消える)、(b) ユーザーが `!` 実行で settings.json の登録と
  `.claude/hooks/tdd_*.py` 3本を削除、(c) フック追加前のコミットへ戻す
  (`.claude/hooks/` は追跡対象なので git で復元できる)。
- **シェルの OS 依存**: 記録した OS と異なる環境での再実行は保証外(設計判断表)。
- **Bash 迂回**: `sed -i` やリダイレクトによるテスト編集は検知できない(設計書 non-goal 1・ADR-0006)。
  補助線として受け入れる。
- 検討した代替案と不採用理由:
  - **案A: Stop フックでの事後検知(codex_gate 型)** — Bash 迂回も拾えるが、改変が起きた後の検知になり
    差し戻しコストが高い。ADR-0006 で PreToolUse 即時ブロックに決定済み。不採用。
  - **案B: settings.json を `json.load` / `json.dump` で書き換える** — 実装は素直だが全体が再整形され、
    無関係な差分が出て最小diff規律に反する。判定・検証のみ JSON パースで行う折衷を採用。
  - **案C: pytest を使わず verify-hooks ケースだけで受け入れを行う** — 重複は減るが、staging 適用
    (ユーザーの `!` 実行)まで1件もテストを走らせられず、テストファーストが成立しない。不採用。
  - **案D: センチネルと blocks.log を `PROTECTED_PATH_PATTERNS` に追加する** — 偽装耐性は上がるが、
    `_common.py` の変更で staging の影響範囲が広がる一方、`/checkpoints/` は既に Edit/Write が塞がれて
    おり増分が小さい。設計書 non-goal 4 とも整合しないため不採用。
  - **案E: R-006 を hypothesis のプロパティテストで書く** — 網羅性は高いが新規依存が増え、
    設計書が許容する verify-hooks の表記変形ケースで足りる。不採用。
  - **案F: センチネルに記録 OS を持たせ、不一致時に解除を拒否する** — 誤判定は減るが、
    センチネルは共有されず別 OS を跨ぐ運用が想定外のため、キー追加より文書明記で足りる。不採用。
  - **案G: staging スクリプトを追跡対象にする(gitignore の例外化)** — クリーン環境でも
    staging 依存テストが走るが、CONTEXT.md の規約と既存 staging 全体の運用を変えることになる。
    2経路方式で同じ偽陰性を塞げるため不採用。
  - **案H: CI で ps1 を Windows ランナー上で実行する** — 実行時の退行まで検知できるが、
    ジョブ追加と Windows 固有の fixture 整備が必要で本計画の範囲を超える。構文検査から始める
    (効果が示されたら別途拡張)。不採用。
