# MLパイプライン修正フロー

Planner/Generator に加え、Evaluator を2軸(Spec/Standards)に分けてレビューする。
フック制御用の環境変数(CLAUDE_WORK_SCOPE / CLAUDE_ENFORCE_EVAL / CLAUDE_EVAL_CMD)は
`.claude/settings.local.json` の `env` ブロックに設定する
(README「起動(フックの有効化)」の節を参照)。

対象に設計書(docs/active/)がある場合、`CLAUDE_SPEC_CHECK=1` を設定すると
Stop フックの `spec_gate` が「## 受け入れ条件」テーブルの全要件PASS・承認・監査OKを
機械検査し、欠けがあれば完了をブロックする。manual要件はユーザーが
`! uv run python .claude/hooks/spec_approve.py <要件ID>` で承認するまで通らない。
設計書自体もユーザーの計画承認(上記の要件承認時に自動記録、または
`! uv run python .claude/hooks/spec_approve.py --design <設計書名>`)が必要で、
承認時点のハッシュと照合されるため、承認後に設計書を書き換えるとブロックされる
(設計書を正当に更新した場合はユーザーに再承認を依頼する)。
spec_approve.py はユーザーの `!` 実行専用で、エージェントの Bash 経由の実行は
guard_bash がブロックする。

## 前提: 作業スコープの確定
- $ARGUMENTS の冒頭で作業ディレクトリ(例: projects/Deep_MIL)が指定されていれば、それを作業スコープとする。
- 指定がなければ、着手前にユーザーに「どのプロジェクトディレクトリで作業するか」を必ず確認する。
- 各エージェントへのタスク指示には作業スコープを必ず明記する。
  `git diff` / `git add` は作業スコープにパスを限定させる
  (例: `git diff -- projects/Deep_MIL/`、`git add projects/Deep_MIL/`)。

## 自律度レベル(CLAUDE_CONTROL_LEVEL)

環境変数 CLAUDE_CONTROL_LEVEL でパイプライン全体の自律度を一括制御する。
個別の環境変数(CLAUDE_AUTO_APPROVE 等)が明示的に設定されている場合は
個別変数を優先する(上級者向けの上書き)。ここで「明示的に設定されている」とは
値が空文字列でないことを指す(空文字列は「未設定」として扱う。既存フックが
`!= "1"` で判定しているのと同じ規約)。

**自律度レベルで制御したいゲートの個別変数は、出荷時に `""` にしておく**。
非空の既定値(`"0"` 等)が入っていると、それが「明示的な設定」とみなされて
自律度レベルより常に優先され、レベルの切り替えが効かなくなる
(例: `CLAUDE_AUTO_APPROVE: "0"` のままだと `CLAUDE_CONTROL_LEVEL=L3` にしても
自動承認が有効にならない)。

| レベル | 名前 | 動作 |
|--------|------|------|
| L1 | 手動運転 | 計画承認は必ず人間(plan-reviewer 無効)。**各実装ステップ完了ごとに diff を提示して承認を待つ**(手順5のステップ承認)。マージ確認は diff 全文の提示つき |
| L2 | 監督運転(既定、未設定時) | 計画承認+マージ確認のみ人間(現行の動作)。実装中は自律 |
| L3 | 自律運転 | plan-reviewer による自動承認を有効化(CLAUDE_AUTO_APPROVE=1 相当)。完了・エスカレーション時に通知(CLAUDE_NOTIFY=1 相当)。人間はマージ確認のみ |

L1 は安全側の指定なので、**L1 のときは個別変数による自動承認の有効化を行わない**
(`CLAUDE_CONTROL_LEVEL=L1` かつ `CLAUDE_AUTO_APPROVE=1` なら、計画承認は人間が行う)。
個別変数の優先はゲートを**弱める**方向には働かない。

レベルを解決するのは原則このプロンプトだが、通知だけはフック(notify.py)が
自前で解決する — Stop フックはプロンプトを経由せずに走るため。notify.py は
`CLAUDE_NOTIFY` が空文字列のときに限り `CLAUDE_CONTROL_LEVEL=L3` を通知ONと
みなす(非空の個別変数を優先する上記の規約どおり)。他のフックはレベルを読まない。

どのレベルでも変わらないもの:
- invariants.md の「人間の承認が必須の操作」(30分超の学習、invariants 変更、
  外部公開)は必ず承認を取る
- permissions.deny の禁止事項は絶対に実行されない
- no-guess 規律(不明点は必ず質問)は全レベルで有効

## 手順
### 0. ルーティング(規模判定)
router(Haiku)に依頼内容を渡し、規模(S/M/L)を判定させる。

- **S(単一ファイル・非ロジック変更)**: planner を省略し、generator に直行する。
  実装後、変更内容の diff をユーザーに提示して確認を取り、コミットする。
  evaluator も省略する(ロジック変更が無いため)。**ブランチは手順1.5 に従い
  常に作成する**(main への直接コミットは自律度レベルに関わらず行わない)。
- **M(単一モジュール・ロジック変更)**: planner を省略し、generator → evaluator の
  短縮経路で実行する。ブランチ作成(手順1.5)と evaluator の判定は通常通り。
  evaluator が NEEDS_REVISION を2回出したら、フルパイプラインに昇格する。
  昇格時は**コミット済みの実装をブランチ上に保持したまま**手順3(計画の作成)へ
  進む。planner には既存差分(`git diff`)と evaluator の指摘全文を渡し、
  現状を前提にした計画を作らせる。
- **L(それ以外)**: 手順1以降のフルパイプラインを実行する。

**リスク階層による経路強化**: router は規模判定と同時にリスク階層(高/中/低)も
返す(**計画の「リスク」セクション(plan-reviewer 条件2)とは別の軸**。同名の概念が
2つできることに注意する)。

| リスク階層 | 作用 |
|---|---|
| 高 | 規模判定を1段上げる(S→M、M→L。L はそのまま)+ 手順6.3(反証濾過パス)を実行しない |
| 中 / 低 | 現状どおり(規模判定を変えない) |

リスク軸は**強める方向にのみ**作用させる。低リスクでも既存工程を省略しない。

router の判定と異なる経路をユーザーが指定した場合($ARGUMENTS に
「フルで」「計画を立てて」等がある場合)、ユーザーの指定を優先する。
自律度レベルが L1 の場合、S/M でも規模とリスク階層の両方の判定結果をユーザーに
提示して確認を取る。

### 0.5. 要件ヒアリング(規模連動)
router の規模判定に応じて、planner に渡す前に依頼内容の曖昧さを解消する。

- **S**: スキップする(非ロジック変更のためヒアリング不要)。
- **M**: design-interview の曖昧性タクソノミー(境界値 / 例外系 / 状態・順序 /
  データ / 非機能 / スコープ境界)を基準に、依頼文に答えの無いカテゴリから
  **最大3問**だけリーダー自身がユーザーに質問する(design-interview スキル
  全体は起動しない)。質問の作法は design-interview の手順5〜8 と同じ
  (1問ずつ・推奨案を添える・環境を調べれば分かる事実は自分で埋め、
  決定はユーザーに出して回答を待つ)。
- **L**: design-interview スキルを実行する(対象の設計書があれば設計書を
  対象に通常フロー。無ければ依頼文を対象に質問し、確定した決定を
  **節録版設計書(受け入れ条件テーブル付き)として docs/drafts/ に必ず生成する**。
  詳細はスキル側の「呼び出しコンテキストによる分岐」を参照)。
  M からフルパイプラインに昇格した場合(手順0の昇格規定)も L として扱う。

確定した回答は「確定要件」として手順3の planner への指示に必ず全文含める
(L では生成した設計書のパスを渡す)。ユーザーが「お任せ」と明示した項目は、
推奨案を提示して確認を取った上で確定要件に含める(no-guess 規律)。
手順3.3 の spec-checklist ゲートは従来どおり実行する(前倒しヒアリングは
事後ゲートの代替ではない)。

**機械ゲート(CLAUDE_REQUIREMENTS_GATE=1 のとき)**: PreToolUse フックの
requirements_gate が、受け入れ条件テーブル付きの設計書が docs/active/・
docs/drafts/ に1つも無いまま計画ファイル(.claude/plans/*.md)を書き始める
ことをブロックする(手順0.5 の実施漏れに対する補助線)。テーブルの中身の
妥当性検査は spec-checklist(手順3.3)と spec_gate(CLAUDE_SPEC_CHECK=1)が担う。

### 1. 作業スコープの確定
作業スコープを確定する(上記参照)。

### 1.5. 作業ブランチの作成
現在のブランチを記録してから、branch-naming スキルでブランチ名を決定する。

- プロジェクトに命名規則がある場合(CONTRIBUTING / README / 既存ブランチの
  実績等から branch-naming スキルが検出): その規則に従った名前
- 無い場合: `pipeline/YYYYMMDD-<トピック>`(<トピック> は依頼内容から
  2〜3語の英語スラグ)

決定した名前でブランチを作成しチェックアウトする。

```
git checkout -b <決定したブランチ名>
```

以降、全ての git add / git commit はこのブランチ上で行う。
main ブランチには一切コミットしない(並列実装時のサブブランチ(/group-A 等)は、
この決定したブランチ名を親としてその配下に作る。命名規則の探索は親ブランチ名の
決定にのみ使う)。

### 2. 事前調査
- 作業スコープ直下に CONTEXT.md があればここで一度だけ読み、用語の要点を
  以降の各エージェントへのタスク指示に含める(各エージェントに再読させない)。
- 対象コードの範囲が広い場合は、planner を起動する前に Explore サブエージェント
  (Haiku)で大まかな下調べを行い、その要約を planner への指示に含める
  (Opus の調査トークンを節約するため)。

### 3. 計画の作成
planner に「やりたいこと」+ 確定要件(手順0.5)+ CONTEXT要点 + Explore要約を渡し、
作業スコープ内を調査させて実装計画を作成させる。計画には並列化判定(並列化可能 / 逐次のみ)を含める。

### 3.3. 設計書・計画の品質ゲート(必須)
Planner が計画を作成するたびに、spec-checklist スキルを**必ず**実行する
(環境変数によるスキップは無い)。

検査対象:
- 設計書を渡されている場合: 設計書 + 計画(トレーサビリティ表含む)
- 設計書が無い場合: 計画そのもの

判定による分岐:

**READY の場合:**
手順3.4へ進む。

**NEEDS_WORK の場合:**
design-interview スキルを**必ず**実行する。
- spec-checklist の指摘(MEDIUM 以上)だけを対象に、1問ずつユーザーに
  確認して解消する(全カテゴリの再インタビューはしない)
- 設計書がある場合は設計書を更新する。設計書が無い場合は、解消した
  内容を planner に渡して計画を修正させる
- 解消後、planner が計画を更新し(設計書が変わった場合はトレーサビリティ表も
  更新)、再度 手順3.3 の spec-checklist を実行する

このループは最大2周まで。2周しても NEEDS_WORK が解消しない場合は、
残った指摘を提示してユーザーに判断を仰ぐ
(このまま進める / 手動で設計書を直す / 中止)。

NEEDS_WORK が発生した場合、.claude/improvements/feedback.md に
以下を追記する(retrospective の分析対象にするため)。

```
## YYYY-MM-DD [spec-checklist: NEEDS_WORK]
- 指摘の次元: (完全性/明確性/一貫性/測定可能性/カバレッジのどれか)
- 指摘内容: (主要な指摘を1-2文で)
```

### 3.4. 計画プレモーテム(必須)
手順3.4 では、手順3.3 を READY で通過した計画に対して、plan-premortem を
独立コンテキストで起動し、実装前に失敗要因を洗い出す。

渡す情報は**計画ファイルのパスと作業スコープだけ**にする(planner の会話履歴・
検討経緯は渡さない。渡すと「なぜその設計にしたか」という弁明を前提にした判断に
なり、独立した初見レビューという工程の意味が失われる)。

判定による分岐:

**HIGH が1件以上の場合:**
指摘全文を planner に渡して計画を修正させ、**手順3.3 から**やり直す。
この差し戻しは1回まで。2回目の HIGH が出た場合はユーザーに指摘全文を提示して
判断を仰ぐ(手順6.8 の SEND_BACK の回数規約に倣う)。

HIGH が1件以上発生した場合、.claude/improvements/feedback.md に
手順3.3 の NEEDS_WORK と同じ体裁で以下を追記する。

```
## YYYY-MM-DD [plan-premortem: HIGH差し戻し]
- 指摘の次元: (前提の誤り/手順の順序・依存の抜け/検証方法の非検出性/影響範囲の見落とし/並列グループの競合/ロールバック不能性のどれか)
- 指摘内容: (主要な指摘を1-2文で)
```

**HIGH が0件の場合:**
MEDIUM/LOW の指摘があれば、手順8.5 の完全レポート(report.md の「発生した問題と
対処」)に未対応の指摘として記載し、手順3.5(計画の承認判定)へ進む。

**適用範囲**: 手順3.3 を READY で通過した全計画に適用する。ただし手順0の規模判定で
S/M は planner を省略するため手順3(計画の作成)自体に到達せず、本手順の対象は
実質的に L と、evaluator の NEEDS_REVISION 2回で昇格した M だけになる。

### 3.5. 計画の承認判定
自動承認の実効値で動作が変わる。実効値は自律度レベルと個別変数から次のように決める。

- `CLAUDE_CONTROL_LEVEL=L1` → 実効値は常に**無効**(`CLAUDE_AUTO_APPROVE=1` でも人間が承認)
- `CLAUDE_AUTO_APPROVE` が非空 → その値(`1` なら有効)
- どちらでもなく `CLAUDE_CONTROL_LEVEL=L3` → **有効**
- それ以外 → 無効

**実効値が有効(CLAUDE_AUTO_APPROVE=1 相当)の場合:**
plan-reviewer に計画を審査させる。
- plan-reviewer が「自動承認OK」と判定 → ユーザー承認をスキップして手順5(実装)へ
- plan-reviewer が「自動承認NG」と判定 → ユーザーに計画を提示し承認を待つ

**実効値が無効(デフォルト)の場合:**
従来通りユーザーに計画を提示し、承認されるまで進めない。

### 4. 計画の承認(手順3.5でスキップされなかった場合)
計画をユーザーに提示し、承認されるまで進めない。

ユーザーが計画を却下した場合、.claude/improvements/feedback.md に
以下を追記してから計画を修正する
(.claude/improvements/ が無ければ作成する)。

```
## YYYY-MM-DD [planner: 計画却下]
- 却下の理由: (ユーザーの発言を要約)
```

環境変数 CLAUDE_SECURITY_SCAN=1 の場合、同一パイプライン実行内の
ユーザー本人の発言(依頼文・計画承認時の発言を含む)に手順6.6の
セキュリティスキャンにかかるトークン消費のコスト承諾が
含まれているか確認する。含まれていなければ、例文
「スキャンのトークン消費は了解済み」を提示してその場でユーザー本人に
明記を求める。ユーザーが省略を選んだ場合はその旨を記録し、
手順6.6をスキップする旨を明記する(記録は覚え書きであり、判定の根拠は
常に会話内の本人発言)。
**承諾の有効範囲は同一パイプライン実行内のみ**。セッション再開・圧縮などで
本人発言を直接確認できなくなった場合、承諾も省略の選択も無効となり、
手順6.6で再度確認する。

### 5. 実装
**実行前承認(全レベル共通)**: 以下のいずれかに該当する操作を行う直前は、
自律度レベルに関わらず必ずユーザーの承認を得る。
提示は3点のみ: **実行内容 / 推定コスト(時間・計算資源) / 不可逆かどうか**。

- 30分を超える学習ジョブの開始(cost_estimate.train_minutes > 30)
- データセットの削除・上書き
- invariants.md 自体の変更
- 外部への成果物公開

計画の並列化判定を確認する。

**generator への共通指示(並列・逐次とも、完了報告に含めさせる)**:
- ある挙動を説明する記述(README・エージェント定義・スキル・手順書)を変更したら、
  その記述が指す実装・設定を grep で確認し、使ったコマンドと結果を報告に含める
  (`.claude/rules/consistency.md` の規律。担当外のファイルにある食い違いは
  勝手に直さず報告する)
- テストを追加したら、修正前の実装(またはバグを含む実装)に対して実行し、
  追加分が FAIL することを確認して報告に含める。正しい実装で緑になるだけの
  テストは検出力の証明になっていない
- 各ステップに着手する直前に計画ファイルの該当ステップ行を読み直し、
  対象ファイル・依存・並列グループを確認してから作業する
- 完了報告と計画ファイル末尾の作業ログの**両方**に「計画ステップ対応表」
  (`| 計画ステップ# | 実施内容 | 変更ファイル | 検証コマンドと結果 | コミットID |`)を
  含める。計画に無い変更はステップ# を「計画外」とし理由を1文添える。
  **ただし並列実装の場合**、各 generator は worktree 内から計画ファイルに
  直接追記しない(サブブランチごとの追記が並列にコンフリクトするため)。
  対応表は完了報告にのみ含め、計画ファイルへの反映は手順6.5でマージした後、
  リーダーが統合ブランチ上で各グループの対応表をまとめて一括追記する。
  逐次実装では従来どおり完了報告と計画ファイルの両方に書く

**計画遵守の照合(必須)**: リーダーは、計画の実装手順のステップ数を
`grep -cE '^\| [0-9]+ \|' <計画ファイル>` で数え、generator の完了報告の
計画ステップ対応表が全ステップ番号を覆うことを確認する。並列実装では
グループごとの表を合算して全ステップを覆うことを確認する。

欠落時は generator に未実施の理由を確認し、「計画の前提が誤っていた」なら
手順3(計画の見直し)へ、単なる実施漏れなら手順5に差し戻す。確認は1回まで、
2回目はユーザーへ判断を仰ぐ。「計画外」行がある場合は変更内容をユーザーに
提示して続行可否を確認する。

注: 以下(手順5・6・6.5・9)の `pipeline/YYYYMMDD-<トピック>` という表記は、
全て手順1.5 で決定したブランチ名の意味で読む(既定形式の例で表記しているだけで、
規約由来の名前(`feature/…` 等)でも同様に読み替える)。

**「並列化可能」かつエージェントチーム機能が使える場合(並列実装):**
並列グループごとの generator チームメイトを **worktree 分離付き**で起動する。
worktree 分離は必須(全エージェントが作業ディレクトリを共有する実行モデルでは
チェックアウトできるブランチが常に1つなので、共有ディレクトリのままでは
グループごとのブランチ分離が成立せず、コミットが混ざる)。

**worktree の作成場所(重要)**: guard_scope は「`CLAUDE_WORK_SCOPE`、未設定ならセッションの
カレントディレクトリ」の配下しか書き込みを許可しない。worktree を作業スコープの外
(`/tmp` 等)に作るとチームメイトの Write/Edit が全てブロックされるため、**worktree は
必ず作業スコープ配下に作る**(例: `.worktrees/group-A`。`.gitignore` に追加しておく)。

```
git worktree add -b pipeline/YYYYMMDD-<トピック>-group-A .worktrees/group-A
git worktree add -b pipeline/YYYYMMDD-<トピック>-group-B .worktrees/group-B
```

各チームメイトへの指示に含めること:
1. 割り当てられた worktree のパスとブランチ名(上記で作成済みなので、
   チームメイト側での `git checkout -b` は不要)
2. 計画で自グループに割り当てられたファイルだけを実装し、
   そのサブブランチにコミットする。他グループのファイルには一切触らない
3. 完了報告として変更ファイル一覧とコミットIDを返す

注意:
- チームメイトが `EnterWorktree` で切り替えられるのは**メインリポジトリに登録された
  worktree だけ**。別リポジトリの worktree は拒否される
- tmux 内で起動していると各チームメイトの進行が分割ペインで見えるが、
  **tmux は表示用であり並列実行の必須条件ではない**(検証済み 2026-07-22)
- worktree 担当エージェントが自分の worktree の外(メインリポジトリ側や他 worktree)へ
  Edit/Write/NotebookEdit で書き込もうとした場合、guard_scope が cwd 基準でブロックする
  (worktree 分離違反の再発防止。Bash 経由のリダイレクト・cp 等は対象外。cwd は
  ペイロード値→os.getcwd() の二段構えで解決し、作業スコープ直下の .worktrees/<名前>
  配下と確定できない場合のみゲートを適用しない安全側の補助線)
- 全工程が完了したら `git worktree remove` で後片付けする

各チームメイトが実装完了したら手順5.5へ進む。

**「逐次のみ」の場合、またはエージェントチーム機能が使えない場合(逐次実装):**
統合ブランチ(pipeline/YYYYMMDD-<トピック>)上で
従来通り generator に逐次実装させる。サブブランチは作らない。
「並列化可能」な計画を逐次実行する際は、その旨と理由を報告する。

generator には計画ファイルのパスを渡して実装させ、完了報告から変更ファイルの一覧を受け取る。

**ステップ承認(CLAUDE_CONTROL_LEVEL=L1 の場合のみ)**:
generator は計画の1ステップを実装するごとに一時停止し、そのステップの
diff(`git diff` の該当部分)と「計画のどのステップか」をユーザーに提示して
承認を待つ。承認されたらコミットして次のステップへ進む。
修正指示があれば同じステップ内で修正して再提示する。
L2 / L3 では従来通りステップごとの停止はしない。

### 5.5. Codex クロスレビュー(条件分岐)
環境変数 CLAUDE_CROSS_REVIEW の値で動作が変わる。
- `1`: cross-review スキルを実行する(codex_gate.py が未実行時にブロックする)
- `0` または未設定: スキップする

cross-review スキルが実行された場合、そのレポートを手順6の
evaluator / evaluator-standards に「Codexからの追加指摘」として渡す。

### 6. レビュー
**過去の失敗パターンの注入(必須。ファイルが無ければスキップ)**:
以下のレビューに入る前に、.claude/improvements/feedback.md があれば
`grep -E '^- (指摘内容|原因/理由):' .claude/improvements/feedback.md | tail -30`
で直近30行を取得し、繰り返し現れる類型を**上位3件まで**選ぶ(30行・3件の上限は
feedback.md の肥大化に伴うトークン節約のため)。選んだ類型は evaluator /
evaluator-standards へのタスク指示に「過去にこのプロジェクトで繰り返された失敗
(参考)。今回の diff に同種の問題が無いか特に確認すること」として渡す。
ファイルが無い、または該当行が0件の場合は注入せず、その旨を手順8.5 の
レポートに明記する。

実装完了後、以下2つを独立に実行する(互いの判断が影響し合わないよう、
それぞれ別の視点でレビューさせる)。両者には変更ファイル一覧を渡し、
diff の確認範囲をそのパスに限定させる。

- evaluator: 計画通りに動作するか(Spec)。評価スクリプトを実際に実行し数値で判定。
- evaluator-standards: コーディング規約・可読性・型安全性・コードスメル(Standards)。

並列実装の場合、レビューは**マージ前のサブブランチを対象**に行う(統合ブランチ上には
まだ各グループの変更が無いため、単純な `git diff` では何も見えない):
- diff の取得はブランチ参照で行う:
  `git diff pipeline/YYYYMMDD-<トピック>...pipeline/YYYYMMDD-<トピック>-group-A`
  (ブランチはリポジトリ共通なので、チェックアウトせずにメインの作業ディレクトリから参照できる)
- evaluator(Spec軸)がテストを実行する場合は、対象グループのサブブランチを
  worktree 分離でチェックアウトした環境で実行する(コード実体が必要なため)。
  このとき `git checkout --detach <サブブランチ>` を使う(同一ブランチは
  実装側 worktree がチェックアウト済みで、通常のチェックアウトは git に拒否される)
- evaluator-standards(Standards軸)は diff の読解が中心なので worktree 分離は不要

evaluator と evaluator-standards はグループごとにチームメイトとして並列実行してよい。

### 6.2. レビュー指摘の接地検証(必須)
evaluator / evaluator-standards /(渡されていれば)cross-review の指摘のうち
**重大度 HIGH と MEDIUM** を対象に、指摘が実在の事実に接地しているかを機械的に
確認する(LOW は差し戻し根拠にならないので対象外。evaluator-standards の
「HIGH/MEDIUM が無ければ基本 PASS」規約と整合させる)。**必須・常時実行だが、
実行されるのは読み取り専用の単発コマンド数本**なのでトークン増は小さい。

証拠の型ごとに検証する:
- **file:line 形式**: リーダーの Read ツールで該当ファイルの当該行付近
  (前後5行)を読み、指摘が名指ししたシンボルがその範囲に現れることを確認する
  (Read は許可プロンプトを伴わないため、必須・常時実行の工程を止めない)。
  行番号がズレている場合は `grep -n '<シンボル>' <path>` にフォールバックし、
  ヒットすれば接地とみなして行番号の相違をレポートに記録する。
- **再現コマンド形式**(「実装が存在しない」等、行を指せない指摘): 添えられた
  コマンドを実行し、報告された出力・終了コードが再現するか確認する。
  **副作用のあるコマンド(書き込み・削除・学習ジョブ)は実行せず「検証不能」**とする。

結果の反映:

| 判定 | 反映 |
|---|---|
| 接地 | 従来どおり根拠にする |
| 未接地・検証不能(MEDIUM) | 根拠にせず手順8.5 のレポートに「未接地の指摘」として記載 |
| 未接地・検証不能(HIGH) | **破棄せず**手順7 の HUMAN_REVIEW 条件1に該当させる |

**判定そのもの(PASS / NEEDS_REVISION / FAIL)は書き換えない**。この工程が絞るのは
差し戻しに使う指摘の集合だけ。並列実装ではグループごとに実施する。

**適用範囲**: 手順6(2軸レビュー)を通る全経路に適用する。手順0 の M 短縮経路
(planner を省略し generator → evaluator で回す経路)でも evaluator の指摘は
差し戻しに使われるため、同じく適用する。S 経路は evaluator を省略するため対象外。

### 6.3. 反証濾過パス(条件分岐)
環境変数 CLAUDE_REFUTE_PASS の値で動作が変わる。
- `1`: 以下の2条件も満たす場合に実行する(いずれかを欠けばスキップして手順6.5へ)
  - 手順0のリスク階層が「高」でない
  - 手順6.2 を通過した HIGH 指摘が1件以上ある
- `0` または未設定: スキップして手順6.5へ

refuter に接地済み HIGH 指摘の全文と変更ファイル一覧を渡す。

反映:
- 反証成功 → 差し戻し根拠から外し、レポートに「反証により棄却された指摘」として
  反証根拠つきで記載する
- 反証失敗 → 差し戻し根拠に昇格する
- 指摘の根拠と反証が**同じ file:line または同じコマンドについて正面から矛盾**する
  → 手順7 の HUMAN_REVIEW 条件3に該当させる

この工程は指摘を**減らす**方向にしか働かないため、リスク階層が高の依頼では
実行しない。既存の「Codex 同箇所指摘で重大度+1」(evaluator.md、
合意方向)は**変更しない**。昇格は反証で、重大度は合意で決めるという併用関係になる。

### 6.5. 原子性チェック(並列実装の場合のみ)
並列グループごとにレビュー結果を確認する。

**全グループが PASS の場合:**
各サブブランチを統合ブランチにマージする。

```
git checkout pipeline/YYYYMMDD-<トピック>
git merge pipeline/YYYYMMDD-<トピック>-group-A --no-ff
git merge pipeline/YYYYMMDD-<トピック>-group-B --no-ff
```

マージコンフリクトが発生した場合はユーザーに報告し判断を仰ぐ。
統合ブランチ上で統合テスト(全テスト実行)を行い、通れば手順6.6へ進む。

**1つでも NEEDS_REVISION の場合:**
他のグループが PASS していても、main へのマージはしない(原子性の保証)。
失敗したグループのサブブランチだけを修正対象として generator に差し戻す。
PASS済みのグループはそのまま保持する。
修正後、失敗グループだけ再レビューする。

**1つでも FAIL(3回連続)の場合:**
全サブブランチの統合を中止する。
ユーザーに報告し、以下の選択肢を提示する。
- 全ブランチを破棄して Planner からやり直す
- 失敗グループだけ破棄し、PASS済みグループは保持して部分的に進める

### 6.6. セキュリティスキャン(条件分岐)
環境変数 CLAUDE_SECURITY_SCAN の値で動作が変わる。
- `1`: 以下を実行する
- `0` または未設定: スキップして手順6.7へ

手順4でユーザー本人が省略を明示している場合は、直ちに手順6.7へ進む
(再確認しない)。ただし、その省略発言をこの時点でも会話内で直接確認できる
場合に限る。セッション再開・圧縮などで直接確認できなければ、承諾の場合と
同様に無効となり、以下で再度確認する。

evaluator と evaluator-standards が両方 PASS した場合のみ実行する。

**(a) プラグインの確認**: claude-security プラグインが導入済みか確認する。
未導入の場合は「claude-security プラグインが未導入のためスキップします。
導入方法: /plugin install claude-security@claude-plugins-official」と
報告して手順6.7へ進む(承諾ゲートには進まない)。

導入済みの場合、到達時点で同一パイプライン実行内のユーザー本人の発言
(依頼文・計画承認時の発言を含む)にコスト承諾があるか確認する(手順4の
記録は覚え書きに過ぎず、エージェントが書いた記録・要約は根拠にしない)。
承諾が確認できなければ黙ってスキップせず、パイプラインを一時停止し
ユーザーに承諾の明記または省略の明示を求める(差し戻し)。

**(b) 差分スキャンの実行**: リーダーが Security Lead として
/claude-security の scan-changes ジョブレシピの手順に従い、
差分(main...HEAD)スキャンを起動する(引数を省略した手組みの
Workflow 直呼びは拒否される)。プラグインの開始確認は、本人の
承諾発言が確認できていればそれを Yes として省略される。それでも
確認質問が表示された場合は、ユーザー本人に直接答えさせ、エージェント
が代答しない。

**(c) 結果の処理**: CLAUDE-SECURITY-<timestamp>/CLAUDE-SECURITY-RESULTS.md を読み、
verification.status が verified の指摘のみを採用する
(unverified の指摘は差し戻しに使わない。参考情報としてレポートに記載する)。

- verified な指摘が1件以上 → severity と file:line を添えて generator に
  差し戻す(手順5に戻る)。プラグインがパッチを提案している場合は
  参考として渡すが、修正の実装は generator が行う
- verified な指摘が0件 → 手順6.7へ進む
- 差し戻しはこの手順経由で最大2回まで。3回目に達したらユーザーに判断を仰ぐ

**(d) 成果物の扱い**: CLAUDE-SECURITY-<timestamp>/ ディレクトリは
コミットしない(プラグイン同梱の .gitignore が防ぐが、念のため
git add にこのディレクトリを含めない)。

### 6.7. リファクタリング・パス(磨きの工程)
evaluator と evaluator-standards が両方 PASS した場合のみ実行する。

**前提**: 開始時点で作業ツリーはクリーンであること(実装は手順5で全て
コミット済みのはず)。クリーンでない場合は磨きを行わず手順6.8へ進む
(後述の復元が「磨きの取り消し」と正確に一致することを保証するため)。

**偵察フェーズ(条件分岐)**: 環境変数 CLAUDE_REFACTOR_SWARM の値で変わる。
- `1` かつエージェントチーム機能が使える場合:
  以下の7体のスカウトを**並列で**スポーンし、対象の差分・ファイルを渡す。
  scout-naming / scout-duplication / scout-complexity / scout-comments /
  scout-symmetry / scout-docstring / scout-deadcode
  各スカウトはコードを変更せず、提案リストだけを返す。

  全スカウトの提案が揃ったら、機械的に統合する:
  - 全提案をファイル:行番号順に並べたリストにする(要約・書き直しをしない)
  - 2体以上が同じ箇所(同一ファイルの±2行以内)を指摘した提案には
    [一致] マークを付ける(優先度高のシグナル)
  - この統合リストを、以降の磨きの工程への入力とする

- `0`、未設定、またはエージェントチーム機能が使えない場合:
  偵察フェーズをスキップし、従来通り実装者自身が下記の観点で
  磨き箇所を探す。

**実装は常に1人**: スカウトの提案があってもなくても、コードを磨くのは
このフェーズの実装者1人だけ。スカウトの提案は参考情報であり、
採用するかどうかは実装者が判断する([一致] マークの提案を優先的に検討する)。
独立した提案を機械的に全部適用することはしない。
**偵察フェーズを実行した場合は、統合リストを実装者(generator)への指示に
必ず含め、[一致] マークの提案を優先的に検討させる**(渡さなければ偵察は
無効になる)。

generator に以下を指示して、動作を一切変えずにコードを磨く1周を行わせる。

**リファクタリングの観点(この順に確認):**
1. **音読テスト**: コードを上から日本語で音読して、自然な文章として
   説明できるか。読めない箇所は、読める形に書き換える。
   - 読める例: `if not is_valid_bag: return None`
     →「有効なバッグでなければ、何も返さない」
   - 読めない例: `if not (b.sz > 0 and b.id in kn): return None`
2. **命名の磨き**: 変数名・関数名を「この文脈でもっと正確な名前」に
   できないか見直す。
3. **コメントの解消**: 処理の説明コメントが必要な箇所を、コメント不要な
   コード(意味の分かる変数への切り出し等)に書き換えられないか。
   why コメントは残す。what コメントはコード化して消す。
4. **簡潔化**: 3行で書けることを5行で書いていないか。
5. **対称性**: 似た処理は似た形になっているか。

**制約:**
- 動作を一切変えない(テストの結果が1つでも変わったら失敗)
- **generator はコミットしない**(下記「リファクタ後」の検証と Standards 再確認を
  通過した後に、呼び出し元がコミットする。先にコミットすると FAIL 時の復元手段
  `git checkout HEAD --` が効かなくなり「復元=磨きの取り消し」の保証が壊れる)
- 新機能・新抽象化を追加しない(これはリファクタであって拡張ではない)
- 既存ファイルの編集のみ。**新規ファイルを作らない**(復元を単純に保つため)
- 変更は磨き対象のファイルのみ。スコープを広げない
- 1周だけ。磨きのループを回さない
- スカウトの提案を採用する場合も、動作不変の制約は変わらない

**リファクタ後(コミット前に検証する):**
- まず `git status` で未追跡ファイルが現れていないか確認する。現れていれば
  制約違反なので削除してから検証に進む(`git diff HEAD` は未追跡を含まないため、
  先に潰しておかないと検証対象から漏れる)
- 計画の検証コマンドと全テストを再実行する(Spec軸の再確認)
- evaluator-standards に**磨きの未コミット差分(`git diff HEAD`。staged 込み)**だけを渡して
  再確認させる(Standards軸の再確認。磨きで命名・構造が変わるため、
  変更前の PASS 判定をそのまま流用しない)
- 全て PASS → refactor コミット(`refactor(step N): <要約>`。
  N は磨き対象の計画ステップ番号、全体の磨きなら計画の最終ステップ番号)をして手順6.8へ
- 1つでも FAIL → `git checkout HEAD -- <磨きで触ったファイル>` で復元し
  (staged 済みの変更も含めて戻る)、
  `git status` に未追跡ファイルが現れていれば削除して(制約違反の後始末)、
  手順6.8へ進む(磨きの失敗で全体を止めない。開始時クリーンが前提なので、
  この復元は「磨きの取り消し」と正確に一致する)

### 6.8. Fable 最終ゲート(条件分岐)
環境変数 CLAUDE_FINAL_GATE の値で動作が変わる。
- `1`: 以下を実行する
- `0` または未設定: スキップして手順7へ

リファクタリング・パスまで全て完了した最終形に対して、final-gate に
以下を渡して最終判断させる:
- 計画ファイルのパス
- `git diff main...HEAD` の差分
- 各レビュー(evaluator / evaluator-standards / セキュリティスキャン)の結果要約
- 最終テストの実行結果

final-gate の判定による分岐:
- **APPROVE**: 手順7へ進む
- **SEND_BACK**: final-gate の示した方向性を generator に渡して差し戻す(手順5に戻る)。
  この差し戻しは1回まで。2回目の SEND_BACK が出たらユーザーに判断を仰ぐ
- **NEEDS_HUMAN**: パイプラインを一時停止し、final-gate が示した判断事項を
  ユーザーに提示して判断を待つ

### 7. 結果の集約
- evaluator が PASS かつ evaluator-standards が PASS: 手順7.5へ
- どちらかが NEEDS_REVISION: 手順6.2・6.3 を経て残った差し戻し根拠を確認し、下記
  HUMAN_REVIEW の条件に該当しなければ、その根拠だけをまとめて generator に
  差し戻す(手順5に戻る)
- evaluator が FAIL(3回連続): planner からやり直すことを提案(手順3に戻る)

差し戻し時のトークン節約(必ず守る):
- 差し戻しは**新規の generator エージェント**に指摘の全文+対象ファイル一覧を
  渡して行う。前回の generator を会話再開で呼び戻さない(全履歴を引きずって
  コンテキストが数十万トークン規模に膨らむ。指摘全文があれば新規で十分)。
- 再レビューは **NEEDS_REVISION を出した軸だけ**に依頼する。PASS 済みの軸は、
  差し戻し修正がその軸の観点(Spec なら動作・要求充足、Standards なら規約・
  可読性)に触れるファイル変更を含む場合のみ再実行する。

**HUMAN_REVIEW(判定不確実の出口)**: 以下のいずれかに該当する場合、差し戻さずに
パイプラインを一時停止し、人間の判断を仰ぐ。

| # | 条件 | 観測 |
|---|---|---|
| 1 | HIGH 指摘が手順6.2 で未接地・検証不能のまま残った | 手順6.2 の結果表 |
| 2 | 軸の判定が NEEDS_REVISION なのに手順6.2・6.3 を経て残った差し戻し根拠が0件 | 指摘集合の件数 |
| 3 | 指摘の根拠と手順6.3 の反証が同じ file:line・同じコマンドについて正面から矛盾する | 両者の実行ログ |

提示するもの: 該当条件 / 当該指摘の全文 / 接地・反証で実行したコマンドと出力 /
選択肢(差し戻す・この指摘を採用せず進む・計画に戻る)。

**注意**: evaluator の判定語彙(PASS / NEEDS_REVISION / FAIL)と verdict の語彙
(PASS / FAIL / UNVERIFIABLE)は**変更しない**(ADR 0003 決定#2)。

**失敗遷移表**: 失敗の種別ごとに、再試行回数と遷移先を以下に固定する。
この表に無い判断(勝手なリトライ継続、勝手な計画変更)をしない。

| 失敗種別 | 再試行 | 使い切ったときの遷移先 |
|---------|--------|----------------------|
| 構文・型エラー(ruff / mypy / import 失敗) | 3回 | generator に差し戻し、それでも失敗なら人間へ |
| テスト失敗 | 2回 | generator に差し戻し、それでも失敗なら人間へ |
| 目標未達(evaluator が fail、guard_metrics 違反含む) | 1回 | planner(計画見直し)へ |
| inconclusive(判定材料が得られない) | 1回 | 原因調査の上、実装起因なら generator、環境起因なら人間へ |
| リソース超過(plan_gate ブロック含む) | 0回 | 停止・人間へ(上限の引き上げは人間だけが決められる) |
| データ読み込み失敗 | 1回 | 停止・人間へ(データの破損・欠損は人間の確認が必要) |
| 判定不確実(上記3条件のいずれか) | 0回 | 停止・人間へ(HUMAN_REVIEW) |

**適用範囲**: 「目標未達」行は goal ブロックを持つ実験計画の三値判定 fail
(および guard_metrics 違反)にのみ適用する。goal の無い計画では、この節の上にある
既存の「evaluator が FAIL(3回連続): planner からやり直すことを提案」が適用される。
各再試行回数は手順8の「最大3イテレーション」の内数とする。

各失敗は発生のたびに .claude/improvements/feedback.md へ
「## YYYY-MM-DD [失敗: <種別>]」の形式で理由を記録する
(retrospective の分析対象になる)。

### 7.5. spec-auditor による独立監査(条件分岐)
対象に設計書(docs/active/)があり受け入れ条件テーブルがある場合、evaluator ×2 の後に
spec-auditor を起動し、verdict ファイルの証拠を独立コンテキストで再検証させる。
spec-auditor が NG を出した要件があれば generator に差し戻す。全件 OK なら完了レポートを出力する。

### 8. イテレーション制限

### 8.5. 完全レポートの生成(必須)
全工程が完了したら(マージ確認の前に)、必ず以下を実行する。

**(a) transcript パスの特定**: `logs/actions/` の JSONL ファイル名末尾の
session 8桁を取り、`~/.claude/projects/` 配下の作業ディレクトリに対応する
プロジェクトディレクトリ内で `<session-id>.jsonl` に前方一致するファイルを
選ぶ。一致が無い、または複数ある場合は mtime 最新の1件を採用する。
どちらも不可能な場合は transcript なしで進める。
**特定の経緯(曖昧一致・特定不能)の記録は、(b) の report_gen 実行後に
evidence/README.txt へ書く**(report_gen は生成前に evidence/ を作り直す
ため、先に書くと消える。黙って省略しない)。

**(b) evidence/ の機械集約**:
```
uv run python .claude/hooks/report_gen.py <実行日時: YYYYMMDD-HHMMSS> --transcript <特定したtranscriptパス> --test-cmd "<計画の検証コマンド>"
```
transcript が特定できた場合は `--transcript` を付けて実行する
(report_gen 内でマスキングを通した上で `evidence/transcript.jsonl` に
コピーされる)。特定できなかった場合は `--transcript` を省略して実行する。
作業スコープのテストが既定の `tests/` の外にある場合は `--test-cmd` に
計画の検証コマンドを渡す。**単一コマンドのみ**(シェルを介さず実行される
ため `&&` や `|` 等のシェル構文は不可。パイプを含む検証コマンドは、
pytest 等の中核コマンド1つに読み替えて渡す)。省略時は既定の
`tests/` のみが evidence/test-output.txt に入る。使われたコマンド・
終了コード・タイムアウトの有無は stats.json に記録される。
diff・コミット一覧・actions.jsonl・agents.jsonl・runs/・
テスト全出力・stats.json が docs/reports/<実行日時>/evidence/ に生成される。

**(c) report.md の執筆**: docs/reports/<実行日時>/report.md を書く。
必須セクション:

1. **概要**: 何を依頼され、何が完了したか(3文以内)
2. **時系列**: 計画→(承認)→実装→レビュー→(差し戻しがあれば各回)→
   リファクタ→最終判定 の各段階で、どのエージェントが何をしたか
3. **各エージェントの判断理由**: planner / plan-reviewer / evaluator /
   evaluator-standards /(実行された場合)spec-checklist / final-gate の
   判定とその根拠の要約
4. **人間の承認コンテキスト**: ユーザーが承認・判断した箇所すべて
   (計画承認の有無と方法(手動 / plan-reviewer 自動)、差し戻し時の指示、
   マージ確認の結果)を時刻つきで記録する
5. **発生した問題と対処**: 差し戻し・失敗・スキップされた工程とその理由
6. **証拠**: evidence/ 内の各ファイルへの相対リンクと stats.json の統計
   (ツール実行数、エージェント実行数、変更ファイル数)、および
   evidence/test-output.txt から引用したテスト数

執筆ルール:
- 各主張は evidence/ 内のファイルを参照する形で書く(証拠の無い主張を書かない)
- 「概ね」「おそらく」で結果をぼかさない。数値はログから引用する
- 失敗・スキップも省略せず書く(完全性が目的。良く見せることが目的ではない)

**(d)** 手順9(マージ確認)でユーザーに提示する情報に、レポートのパス
(docs/reports/<実行日時>/report.md)を必ず含める。

### 9. マージ確認
全工程が完了したら、ユーザーに以下を提示する。

- 作業ブランチ名: pipeline/YYYYMMDD-<トピック>
- コミット数: N件
- 変更ファイル数: `git diff --stat main...<ブランチ>` の結果
- 並列化した場合: 各グループのマージ状態
- 全変更の要約: 1〜3文
- レポートパス: docs/reports/<実行日時>/report.md

そして「mainにマージしますか?」と確認する。

- **「はい」**: `git checkout main && git merge <統合ブランチ> --no-ff` を
  実行し、マージ完了を報告する。`--no-ff` でマージコミットを残し、
  パイプライン実行の単位が履歴で分かるようにする。
  マージ後、サブブランチを削除する。
- **「diffを見せて」**: `git diff main...<統合ブランチ>` を表示する。
  確認後、改めてマージするか聞く。
- **「いいえ」**: ブランチをそのまま残して終了する。
  「後でマージしたい場合は `git checkout main && git merge <ブランチ>`
  を実行してください」と案内する。
- **「全部捨てて」**: 統合ブランチとサブブランチを全削除し、main に戻る。
  main は無傷。

**センチネルの更新(CLAUDE_CROSS_REVIEW=1 のときのみ)**: 「はい」(マージ後)と
「全部捨てて」(main 復帰後)は HEAD が移動するため、最後に

```
git rev-parse HEAD > .claude/checkpoints/codex_review_done.txt
```

を実行してセンチネルを現 HEAD に合わせる。更新しないと codex_gate が旧コミットを
指したままの センチネルと現 HEAD の不一致を検出し、Stop をブロックし続ける。

**ただし無条件ではない**。この更新が形骸化に当たらないのは、現 HEAD の内容が
レビュー済みと同一視できる場合だけ:
- 「はい」: マージが**競合なしで**完了し、かつマージ先の main が最終レビュー
  時点から**進んでいない**場合のみ(競合を解消した場合や main が並行更新されて
  いた場合、その内容は未レビューなので、更新せず cross-review を再実行してから
  作成する)
- 「全部捨てて」: 復帰した main がブランチ作成時点から**進んでいない**場合のみ。
  判定は**ブランチを削除する前に** `git rev-parse main` と分岐点
  (`git merge-base main HEAD`)を比較し、両者が一致することで行う
  (merge-base 単体では main の前進を検出できない。進んでいた場合、その分は
  このセッションのレビュー対象外なので cross-review を再実行してから作成する)
- 「いいえ」: ブランチ上に留まり HEAD が動かないため更新不要

$ARGUMENTS を「作業スコープ + やりたいこと」として解釈する。
